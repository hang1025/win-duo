# Win Duo 开发过程记录

这份文档记录 Win Duo 从一个问题开始到能用的全过程：每一阶段做了什么、每个结论是怎么得出的、以及踩过的每一个坑是怎么被发现的。

面向读者是「会一点编程、想复刻或学习这个项目的人」。所以重点不在结论，而在**结论是怎么被验证出来的**——这个项目里几乎每个真 bug 都不是靠读代码看出来的，而是靠某种测量手段抓出来的。

平台：Windows 11 Pro for Workstations，AMD Ryzen 7 5800H，NVIDIA RTX 3050 Laptop + AMD Radeon 双显卡，联想 XiaoXinPro 16ACH 2021（机型号 82L5），屏幕 1707×1067 DIP @1.5× 缩放，即 2561×1601 物理像素，实测刷新 120Hz。

---

## 0. 起点

iPhone Duo 发布后，真正出圈的不是铰链本身，而是它开合时那段**透视动画**：屏幕折起来的时候，内容不是被折痕挡住消失，而是带着透视向后倒、越远越糊越暗，读起来像一块连续的物体在空间里转动，而不是一块面板被关掉。

macOS 上的参考实现是 [Mac Duo](https://github.com/sumimakito/Mac-Duo)，作者 Makito。它做的事情是：合盖时把你屏幕**当前的画面**做同样的透视变形。我们想做一个 Windows 版。

问题的核心很快就清楚了：**Mac Duo 之所以能"跟着手走"，是因为它读得到真实的合盖角度。**而普通 Windows 笔记本没有这个东西。所以整个项目其实分成两半：

1. 把效果本体（几何 + shader）移植过来——这部分是纯数学，可移植。
2. 解决"角度从哪来"——这部分只能在 Windows 上重新想办法。

## 1. 第一阶段：效果本体是什么

### 1.1 读参考实现

把 Mac Duo 克隆到本地读源码。它由这几块组成：

| 文件 | 作用 |
|---|---|
| `Sources/LidAngleKit/LidAngleSensor.swift` | 读合盖角度传感器 |
| `Sources/MacDuo/DepthOverlay.swift` | 几何计算 + 覆盖层窗口 |
| `Sources/MacDuo/Homography.swift` | 单应矩阵（Heckbert square-to-quad） |
| `Sources/MacDuo/DepthShaders.swift` | **整个效果，一个 Metal fragment shader** |
| `Sources/MacDuo/DepthRenderer.swift` | 逐帧渲染 + 高斯金字塔 |
| `Sources/MacDuo/LidController.swift` | 触发与进出策略 |
| `Sources/MacDuo/CriticallyDampedSpring.swift` | 弹簧平滑 |
| `Sources/MacDuo/BlurGradient.swift` | 模糊/压暗曲线 |

关键发现：**效果本体比想象的小得多**。核心就是"一次截屏 + 一个按屏幕高度做透视、模糊、压暗的 shader"。

那一段 Metal shader 的全部内容（这是灵魂）：

```metal
// 屏幕像素 → 画面像素（逆单应）
float3 mapped = screenToPicture * float3(screenPoint, 1.0);
float2 picturePoint = mapped.xy / mapped.z;

// 归一化到画面高度：0 在铰链边，1 在远端
float height = clamp(picturePoint.y / screenSize.y, 0.0, 1.0);

// 想要多糊 → 决定取哪一级 mip（高斯金字塔）
float blur = strength * (blurFloor + (1.0 - blurFloor) * height);
float mipLevel = clamp(log2(max(blur * maxRadius, 1.0)), 0.0, maxLevel);
float4 colour = picture.sample(linearSampler, texCoord, level(mipLevel));

// 按高度压暗
float spread = smoothstep(0.0, max(dimReach, 0.02), height);
float fade = dimStrength * (dimFloor + (1.0 - dimFloor) * spread);
colour.rgb *= pow(1.0 - maxDim * fade, 2.2);
```

**按高度渐变就是全部的诀窍**：铰链那一侧保持清晰明亮，越往远端越糊越黑，叠加透视收缩，读起来就是"一整块表面在折走"。

模糊是白送的：画面只上传一次，四周留 120 点黑边，然后建 mip 金字塔。"这里要糊多少"就只是按对应层级做一次 `textureLod`。层级之间做插值，还能盖掉减半金字塔在大半径下会出现的块状感。

另外两处值得注意：

- 原版在画面范围外返回 `float4(0.0, 0.0, 0.0, 1.0)`——**不透明黑**。这一点后来成了我们最大的一个 bug（见 §5.2）。
- 压暗用的是 `pow(1 - maxDim*fade, 2.2)`。因为原版采样的是 sRGB 纹理，数学跑在 linear light 里，这个 2.2 恰好抵消回"编码空间里的线性衰减"。我们移植时不解码纹理，所以直接乘 `(1 - maxDim*fade)` 即可。

几何部分（`DepthGeometry.corners`）：把画面当成一块**以屏幕下边缘为轴**的板子，眼睛是房间里一个固定的点，玻璃在眼睛下方转动。把板子投影回玻璃平面，得到四个角点，交给单应矩阵。默认参数：`recession = 1`（板子转开多少度 = 盖子转多少度）、`maxSeparationDegrees = 88`（再转就背面朝你了）、`viewingDistance`（眼睛距离，单位是屏高）。

### 1.2 移植到 Electron

Electron 44.3.0（Node 24.20.0）。选它的理由是：透明窗口、穿透点击、屏幕截取、托盘、全局快捷键全都开箱即用，**不需要任何原生模块**——别人 `npm install` 就能跑。

零原生依赖是刻意维持的，包括图标：托盘图标和窗口图标都是用代码画出来再用 `zlib` 编码成 PNG/ICO 的，仓库里没有任何二进制素材。

### 1.3 验证方式：离屏渲染成 PNG 自己看

这是第一阶段最重要的决定。**没有第二台机器做对照，且效果的几何很容易"错得很像对的"**——坐标轴反了或者矩阵转置了，一样能画出一个看起来挺像的扭曲。

所以做了 `npm run selftest`：在离屏窗口里直接把效果渲染到指定角度，导出 PNG。

测试图是故意设计的：网格 + **顶部一条红杠 + 底部一条绿杠** + 四面字母标注 + 中间一个圆。

> 红杠要是跑到底部去了，就是哪里转置了。

第一次渲染的结果（角度 130° 到 20°）：

- 130°/110°/95°/90° 四张 PNG 的**字节数完全相同**（184158），因为它们都落在"板子还没开始转"的区间里，应该是同一张平坦画面。字节一致本身就是个正确的信号。
- 72° 那张呈现出"画面朝远端收窄 + 分级模糊压暗"——这正是预期的方向。

这个手段后来抓到了真问题。等效果接了摄像头之后，同一套图又暴露出"折叠范围过头"（见 §5.6）。

### 1.4 这一阶段踩的坑

**Windows 会把窗口裁到工作区。** 构造时传 1707×1067，实际得到 1708×1020；`workArea` 是 1707×1019。也就是说任务栏那 47 点的一条**没被覆盖**。测下来 `showInactive()` 之后重新 `setBounds()` 才生效（得到 1708×1068），而且要在 `setImmediate` 里再设一次，避免第一次映射时又被裁。

**截屏通道的延迟是固定的。** `desktopCapturer.getSources` 中位耗时 **470ms**，而且**与请求的缩略图尺寸无关**——854×534 和 2561×1601 都是 470–550ms。这是采集会话的建立开销，不是传输。相比之下 `toBitmap` 只要 5ms（15.6MB）、`toPNG` 160ms（824KB）、`toJPEG(92)` 22ms（483KB）。

端到端计时（`WIN_DUO_DEBUG=1`）：

```
+   0ms  grabbing the screen
+ 501ms  screen grabbed
+ 524ms  handed to the overlay
+ 612ms  picture-built        （16.4 MB 位图完成通道交换、上传、建 mip 金字塔）
+ 614ms  first-frame
```

即 **热键到首帧约 0.6 秒，其中 0.5 秒是那一次截屏**。想干掉它就得常驻一条实时采集流，用"永远开着的屏幕采集会话"换这半秒。对一个玩具性质的效果不划算，所以留着并如实记录。

**自检脚本自己的噪声。** `--verify` 曾经偶发失败，查出来是脚本自己在 `trigger()` 期间连续截屏、把主进程堵住了：`play()` 内部出现 352ms 的假延迟。加一个独立的 `--timing` 模式（只触发一次、不做其他事）之后，`play()` 内部耗时只有 23ms。**测量手段本身会污染测量结果**，这件事后面还会再出现一次。

## 2. 第二个困难：Windows 笔记本没有合盖角度传感器

### 2.1 先确认它确实不存在

Mac Duo 读的是一颗 Apple 专用器件：`AppleSPUHIDDevice`，vendor `0x05AC` / product `0x8104`，HID usage page `0x20` / usage `0x8A`，两个 report（report 1 是 3 字节整度 0–360，report 7 是 5 字节小端百分度），约 100ms 刷新一次，不需要任何授权。

Windows 上对应的 API 是 `Windows.Devices.Sensors.HingeAngleSensor`。但微软文档的原文定义是：

> *"Represents the hinge angle sensor in a **dual-screen device**."*

它是给 Surface Duo / Neo 这类双屏设备用的。消费级笔记本上根本没有这颗器件。

**但我们没有只信文档，而是去实测了。** 用 Windows PowerShell 5.1（.NET Framework 有完整的 WinRT 投影）逐个探测 `Windows.Devices.Sensors` 下的 14 个类：

```
Accelerometer|ABSENT          Inclinometer|ABSENT
ActivitySensor|ABSENT         LightSensor|ABSENT
Altimeter|ABSENT              Magnetometer|ABSENT
Barometer|ABSENT              OrientationSensor|ABSENT
Compass|ABSENT                Pedometer|ABSENT
Gyrometer|ABSENT              ProximitySensor|ABSENT
                              SimpleOrientationSensor|ABSENT
                              HingeAngleSensor|ABSENT
```

**14 个类，0 个有实例。** 也就是说这台机器上一个 Windows 传感器都没有：没有铰链角度，没有加速度计，也没有环境光传感器。

顺带确认了硬件层：设备管理器里只有一个传感器设备 `HID\ITE8350&COL02\4&39e466f8&0&0001`（ITE8350 传感器集合，HardwareID 含 `HID\VID_048D&UP:0020_U:0001`，由微软的 `SensorsHIDClassDriver` 驱动）。而光照传感器的设备接口类 `{97f115c8-599a-4153-8894-d2d12899918a}` 在注册表里存在，但**只有一个 `Properties` 子键、没有任何设备实例**。

结论：Windows 上拿不到连续角度，只能找**替代信号**。

### 2.2 探测脚本自己出的错（值得记住）

第一版探测报告说：

```
✅ ActivitySensor
✅ Pedometer
✅ HingeAngleSensor
```

**一台根本没有铰链传感器的机器，报告说有。** 原因是 `GetDefaultAsync()` 返回的是 `IAsyncOperation` 对象，而那个对象**永远不为 null**——即使机器上没有任何该类型传感器。把它当传感器对象判断，就会对每一个"只有异步接口"的类误报存在。

修法是加一个 `IsSensor` 判定：真传感器一定有 `DeviceId` 属性，且类型名里不会出现 `AsyncOperation`。

> 这是最危险的一类 bug：它会把使用者引到完全错误的方向上。所以探测结果必须用第二种证据交叉验证（这里用了设备接口类的注册表项）。

### 2.3 PowerShell 执行策略

Windows 客户端默认执行策略是 `Restricted`，写一个 `.ps1` 到磁盘再运行会被拒绝。所以脚本是用 `-EncodedCommand`（UTF-16LE base64）**内联**传给 `powershell.exe` 的——**执行策略只管脚本文件，不管内联命令**。这样在出厂设置上就能跑，不需要用户改任何东西。

## 3. 第三阶段：找替代信号

写了 `tools/lid-recon/`：一个只做测量、不做效果的侦察器。它录下所有候选信号，然后回答一个问题——**有没有哪个物理量随盖子角度单调变化？**

### 3.1 四个候选，以及为什么只剩一个

| 候选 | 物理依据 | 结论 |
|---|---|---|
| 环境光传感器 | 合盖改变照度 | ❌ **根本没有这个传感器**（§2.1） |
| 声学（喇叭→麦克风） | 喇叭在底座、麦克风在盖子上，合盖时距离从约 25cm 收到约 2cm，传递函数剧烈单调变化 | ❌ 见下 |
| Wi-Fi RSSI | 天线在盖子顶部，合盖时与底座耦合改变 | ❌ 必须连着 AP、天线还不一定在盖子上、多径导致非单调 |
| **摄像头** | 摄像头刚性固定在盖子上 | ✅ 唯一普适的 |

**声学那一路的致命伤是一个物理事实**：3.5mm 耳机口里有机械开关触点，插头一插进去，**内置扬声器的功放就被断开了**。探测音会送进耳机，内置喇叭根本不发声，"底座喇叭 → 盖子麦克风"这条路径压根没建立。

而"戴着耳机工作"是常态——**用户自己就是第一个中招的**。这不是边缘情况，所以声学不能作为主方案。

**Wi-Fi 那一路，用户自己也立刻是反例**：当时那台机器 Wi-Fi 是 `Software Off` 且 `disconnected`，走的是 Realtek USB 有线网卡。一个只在"连着 Wi-Fi 且天线恰好在盖子上且路由器位置合适"时才生效的方案不成立。

于是只剩摄像头。

### 3.2 摄像头的物理依据（这是它能成立的全部原因）

> 每台笔记本的摄像头都是**刚性固定在盖子上**的。盖子转 Δθ，摄像头就转 Δθ，画面里的整个场景随之平移 `f·tan(Δθ)`。

精度估算：

| 项 | 数值 |
|---|---|
| 640px 宽、60° 视场 | 焦距 f ≈ 520 px |
| 盖子转 1° | 画面平移 **9.1 px** |
| 亚像素相关能做到 | ~0.1 px |
| ⇒ 角度分辨率 | 约 **0.01°** |
| 实际需要 | ±2° |

**余量 200 倍。** 精度从来不是问题，唯一的敌人是"合盖的人自己也在画面里，而且动得比盖子多"。

### 3.3 追踪算法

- 画面缩到 160×120，切成 **8 条竖带**
- 每条竖带各自求行亮度曲线，各自做归一化互相关求竖直位移
- 取 8 条的**中位数**——手和头只污染其中几条，均值会被它们拖走
- 置信度低于 0.7、或方差小于 4（白墙、漆黑天花板）的竖带直接丢弃
- 符号约定：**正数 = 场景向下移动**

### 3.4 引导式协议

为了让不同轮次可比，用固定节奏而不是"随便合盖"：

```
全开保持 2s  →  用 4 秒匀速合上  →  全合保持 2s  →  用 4 秒匀速打开  →  休息 1.5s
```

合上之后看不见屏幕，所以每个相位切换有**提示音**（单音=保持，双音上滑=该动了）。

### 3.5 合成画面自检：第一次就抓到了符号错误

`npm run recon:selftest` 用程序生成的、位移**已知**的画面喂给同一套算法（不打开任何摄像头），验证跟踪值和注入值是否一致：

```
forward : tracked -58.901 rows, injected 60 rows   ← 第一次跑的结果
backward: total came home to 0.998 rows
FAIL
```

**符号是反的。** 跟踪算法把已知位移跟反了——而一个反向跟踪的算法在被接进效果之前，看起来和正确的完全一样。

修法不是改算法，而是**把约定写清楚**：`bestShift` 返回正值表示"场景向下移动"，而滑动源窗口让场景向上移动，所以期望值是负的。修好后：

```
forward : tracked -58.913 rows, injected -60 rows (error 1.09, quality 1, strips 8/8)
backward: total came home to 0.997 rows
PASS
```

误差 1.09/60 ≈ 1.8%，来自抛物线亚像素拟合的小偏差，可以接受（标定会吸收掉固定的比例误差）。

### 3.6 用户实跑的结果

用户按协议跑了 3 次循环（约 40 秒）：

```
camera   能跟，但偏弱   信噪比 106.5   保持漂移 4%   单调 3/3   可逆 2/3
```

逐条读：

| 循环 | 合上（4s） | 全合保持（2s） | 打开（4s） |
|---|---|---|---|
| 1 | −5.8 → −105.8　54 步向下 / 3 步向上 | −107.6 → −143.0　**漂了 35** ⚠️ | 乱（32 上 / 25 下）→ 停在 −108 |
| 2 | +7.3 → −129.3　34 向下 / 3 向上 | −129.3 → −135.3　**只动 6.0** ✅ | −135.3 → −24.6　42 上 / 8 下 |
| 3 | −4.0 → −207.2　45 向下 / 12 向上 | −201.2 → −195.2　**只动 6.0** ✅ | −195.2 → −25.7　41 上 / 6 下 |

四个关键数字：

1. **信噪比 106.5** —— 信号是噪声的一百倍。
2. **单调 3/3** —— 三次合盖每次都是干净的单一方向。
3. **保持漂移 4%** —— **这个数字最关键**。它回答的是"我停住，画面能不能停住"。把盖子停住时，跟踪值只漂了总行程的 4%。
4. **可逆 2/3** —— 第 1 次没干净回来，因为那 2 秒"保持"里用户还在继续合盖子（41 个采样里 23 步都在向下），后面的"打开"窗口从还没停稳时就开始计时了。**那是操作节奏问题，不是追踪器问题。**

结论：**摄像头这条路成立。**

## 4. 第四阶段：接进本体

### 4.1 架构

追踪器抽成 `src/renderer/lib/lid-tracker.js`，**侦察器和覆盖层共用**——两份实现意味着以后修一处漏一处；这次重构之后用自检验证两边结果一致（−58.913 vs −58.901）。

角度来源做成可插拔：`angleSource` 可以是 `camera`（跟随真实盖子）或 `sweep`（脚本动画）。摄像头打不开时**自动回退到脚本动画**并明确告知，而不是留一个死掉的覆盖层在屏幕上。

### 4.2 待命 / 跟踪 / 释放

摄像头指示灯是**硬件直连、软件关不掉**的，所以它不能常年开着。流程是：

1. 按 `Ctrl+Alt+D` 待命 → 同时开摄像头和截屏（并发，不互相拖慢）→ 追踪归零
2. **待命期间画面保持完全透明**（opacity 恒为 0）——桌面保持是活的，不会被一张冻结的截图替换掉
3. 盖子一动 → 淡入（70ms）落在一张没被动过的桌面上
4. 盖子合、停、开，画面实时跟随
5. 结束：盖子回位 / 15 秒无动作 / 5 分钟硬上限，三种之一；或者随时按 **Esc**

### 4.3 方向与标定

**方向不假设。**画面往哪个方向移动取决于摄像头怎么装的、你怎么坐，所以方向从本次运行中**最大的一段位移**的符号里判定；出现更大的反向位移就重新判定。

**满行程自动学习。** 一次完整合盖产生多少画面行程，取决于摄像头、房间和坐姿，不可能写死。所以每次完整合盖都更新一次估计值（新值占 30%），且只接受"走完了至少 60% 的合盖"的样本。每轮运行的追踪值在待命时**重新归零**，所以跨轮次的漂移永远不会累积。

## 5. 接进本体之后发现的 bug

这一节是本文档最重要的部分。**每一个 bug 都是被某种测量手段抓出来的，没有一个是靠读代码发现的。**

### 5.1 折叠进度恒为 0（符号）

`--verify-camera`（用合成画面驱动整条实时链路）第一次跑的结果：

```
armed   {"mode":"camera","opacity":0,"angle":105,"progress":0,"travel":0,...}
closing {"travel":-67.93,"engaged":true,"progress":0,"peakTravel":0,...}
```

`travel` 正确累积到 −67.93、`engaged` 也正确变成了 true，但 **`progress` 恒为 0，`peakTravel` 恒为 0**。

两个原因，同一个根：**合成驱动让场景向上移动，所以 `travel` 是负数，而映射假设它为正**。

- `progress = clamp01(travel / full)` → `clamp01(-0.4)` = 0
- `peakTravel = Math.max(0, travel)` → `Math.max(0, -67.93)` = 0

改成从最大位移自动判定方向之后：

```
closing {"phase":"tracking","opacity":1,"angle":63.05,"progress":0.4,
         "travel":-67.93,"direction":-1,"engaged":true,"peakTravel":67.93}
```

### 5.2 画面范围外的黑写成了透明（**最大的一处移植 bug**）

原版 Mac Duo 在画面范围外返回不透明黑：

```metal
return float4(0.0, 0.0, 0.0, 1.0);
```

移植时写成了：

```glsl
fragColor = vec4(0.0);        // alpha = 0，全透明
```

**而窗口本身是透明的**（为了能淡入淡出）。于是画面折起来、收缩之后，**没被它覆盖到的每一处都让真实桌面原样透了出来——清晰、不变形**。

用户拍的照片里"清晰的桌面图标 + 中间一块模糊内容"就是这个现象。

定位它的手段是**探针**：直接问 shader 在指定屏幕点算出来的纹理坐标是什么，而不是从照片上猜。73° 时：

```
fold 030%（73°）
  bottom5:  covered=true   picture=[854, 4.5]      ← 正常
  top5:     covered=false  picture=[854, 1179.9]   ← 未覆盖
```

**画面远端只到屏幕顶部往下约 80 点，上面那条横向的带子就是泄漏区。**

修复：

```glsl
fragColor = vec4(0.0, 0.0, 0.0, uOpacity);   // 预乘 alpha
```

`uOpacity` 为 1 时是不透明黑，淡出时才是透明。

> 教训：透明窗口里，"范围外"必须是**不透明**黑。这是移植时最容易漏掉、而且看代码看不出来的一处。

### 5.3 死区按"每帧"判断，而屏幕是 120Hz

追踪器的死区是 0.08 行/帧，低于它就算噪声丢掉。问题是**这个阈值取决于帧率**：

- 侦察器采样率只有约 20Hz（815 个采样 / 40 秒），慢速合盖每帧移动约 3 行 → 远高于阈值 → 问题完全没暴露。
- 覆盖层跑在 120Hz，**每帧只移动约 0.2 行** → 压在阈值边缘，一半以上的帧被判成噪声扔掉。

结果：行程永远累积不起来 → 进度接近 0 → 画面几乎不折。

修法是把死区从"每帧"移到**累加器**上：

```js
this.residual += middle;
if (Math.abs(this.residual) > this.deadband) {
  this.total += this.residual;
  this.residual = 0;
}
```

慢速运动先累加、够一个死区就整体提交；零均值的噪声依然无法累积。

### 5.4 释放条件绑在"行程归零"上

合盖到一半时，摄像头从"看着房间（1–2 米）"变成"看着键盘（约 30 厘米）"。而摄像头本身也随盖子**平移**（绕铰链转动同时也在移动），近处和远处的物体在画面里移动速度完全不同——**运动方向可能短暂反向**。

一旦反向够狠，行程掉回阈值以下（当时是 10.2 行）就触发释放 → 画面直接弹平、露出带图标的桌面。

修法是释放判断改成**相对峰值**而不是相对零：只有"确实完成过一次像样的合盖（峰值 > 满行程的 25%）"并且"当前值降到满行程的 10% 以下"才释放。

### 5.5 展开时"冻住 → 跳一下"（从运行轨迹里发现的）

用户报告："模糊有问题，一开始屏幕下端的模糊可以，但随着展开屏幕，效果不大好，然后屏幕上方好像突然由模糊变成清晰那样，没有从下而上的渐变感。"

**这不是靠看画面猜的，而是从用户自己那次运行的 `last-run.json` 轨迹里读出来的。**每次运行都会写一份 100ms 采样：

```
 t(ms)   travel     peak    Δpeak    progress  angle
 3789    -175.8     186.5      0.0      0.766    49.1     ← 冻住
 3889    -145.8     151.8    -34.7      0.726    52.0     ← 跳 35 行
 4189    -121.8     151.8      0.0      0.628    59.2     ← 冻住
 4289    -109.8     115.8    -36.0      0.591    61.9     ← 跳 36 行
 4689     -73.8      79.8    -36.0      0.443    72.7     ← 跳
 5089     -46.2      49.7    -30.1      0.301    83.0     ← 跳
 5589     -21.8      24.8    -24.9      0.166    92.9     ← 跳
```

**展开时画面是"冻住 → 跳一下"重复 5 次，每次约 35 行（约总行程的 20%），约 400ms 一次。**这不是渐变，是在跳。

根因是我上一轮加进去的**棘轮**：反向持续 350ms 之后直接赋值

```js
else if (now - state.retraceAt > settings.retraceHoldMs) state.peakTravel = closingTravel;
```

积压的位移被一次性释放。

改成**非对称跟随**——合上瞬间跟、打开按 250ms 时间常数滑：

```js
if (closingTravel >= state.peakTravel) {
  state.peakTravel = closingTravel;
} else {
  const follow = Math.min(1, dt / settings.releaseFollowSeconds);
  state.peakTravel += (closingTravel - state.peakTravel) * follow;
}
```

修复后同一段轨迹变成平滑的指数衰减：

```
peak 66.2 → 57.5 → 43.7 → 29.2 → 19.5 → 13.0 → 8.6 → 5.7 → 3.8 → 2.5
```

自检里加了针对这一条的断言。实测（合成驱动，100ms 采样）：

```
合上最大步长 24.0 / 26.0 / 26.7 行    ← 驱动本身的真实速度
展开最大步长 15.0 / 15.0 / 15.2 行    ← 比驱动还慢，即平滑跟随
```

### 5.6 折叠范围跟着盖子一路折到 0°，而参考视频只到约 50°

用户报告："黑边太大了。"

此时的证据终于完整了：用户把抖音那段视频下载下来发给了我们。用 Chromium 自己解码抽帧（`tools/extract-video-frames.js`，不需要装 ffmpeg），源是 1280×720、10.54 秒，效果段在 0.53s–6.85s。

逐帧看下来有两件事：

**其一，模糊是对的，我上一轮改错了方向。**视频最深的两帧（2.63s / 3.69s）里，图标已经糊成一团色块，屏幕上方约一半是黑的，**只有底部的 Dock 是清晰的**——这和我们自己 fold-050 的截图几乎一模一样。所以**参考效果本来就是重度模糊**，靠的是"透视收缩 + 顶部渐黑"，不是清晰度。我把模糊从 95 砍到 45 是砍错了，调回 90（`maxDim` 0.85）。

**其二，范围错了。**视频里的人最多只合到约 **50°**，从来不把盖子合到底。而我的映射把整段行程对应到 105°→0°，用户合到底时画面就折到了参考视频里**根本不存在的极端程度**，黑自然吃掉大半屏。

修法是加 `foldAngle`（默认 50）：行程先映射到角度，然后**几何在 50° 停住**。盖子再往下合，画面保持不变。实测输出：

```
fold 100%  angle=50.00  progress=1  travel=-89.92
```

> 注意这里先试错过一次：我最初只是夹住了 `progress`，但几何本身还是折到 0°，最极端的状态没变、只是提前到达了。必须让**几何的角度**封顶，而不是只夹进度。

顺带按参考视频调开了两处渐变参数：`dimReach` 0.5 → 0.9（低于 1 时画面上部会整片变暗，读起来像一条黑带而不是渐变）、`blurCurve` 1.6 → 1.0（大于 1 会让模糊来得晚、然后猛冲）。

### 5.7 `recession` 取 1 时"像甩出去"

`recession` 是"盖子每转一度，画面转开多少度"。原版默认 1，意思是画面钉在房间里、玻璃在它下面转。

**用户在真机上按手感调到了 0.4**，并明确说"画面转开比例，我这个配置刚好"。取 1 时画面转得太快，读起来像"甩出去"而不是"折过去"。

0.4 现在是默认值。

### 5.8 用鼠标点击退出的响应约 700ms

用户报告："鼠标单击退出，反应很慢。"

原因是**两段串行等待**：

```
点击 → 弹簧把画面缓动归平 → 淡出 → 隐藏
```

"归平"用的是跟踪用的弹簧频率 **16 rad/s**。临界阻尼弹簧需要四五个时间常数才能收敛，从半折状态衰减到 0.4% 需要**约 500ms**——这之后才开始 220ms 的淡出。合计约 700ms。

（这段"先归平再淡出"本身是有理由的：直接把一张歪着的图淡掉，会露出底下正常的桌面，看着很跳。所以不能简单砍掉。）

修法是给"归平"一个独立的更快频率 `releaseSpringFrequency: 45`，并让显式结束走更短的淡出 `clickFadeOut: 0.12`。实测**点击到画面消失 281ms**。

### 5.9 最后改成 Esc

用户反馈点击仍然不理想，要求改成 Esc。

改成 Esc 顺带解决了另一个问题：**为了做点击退出，覆盖层必须接管鼠标输入**（`setIgnoreMouseEvents(false)`），副作用是效果显示期间点不了桌面。改用按键之后，点击恢复成**穿透到桌面**（这本来就是 Mac Duo 的行为）。

Esc 的处理有个关键细节：**全局快捷键会把这个键从所有程序手里抢走**，一直挂着会让其他软件的 Esc 全部失效。所以它**只在一次运行期间注册，结束立刻注销**：

```js
function registerExitKey() {
  if (exitKeyRegistered) return true;
  ok = globalShortcut.register('Escape', () => { if (overlay) overlay.requestExit(); });
  ...
}
function unregisterExitKey() { globalShortcut.unregister('Escape'); }
```

它同时也能**取消一次误触发的待命**（盖子还没动、画面还是透明的时候）。

实测 **按键到画面消失 276ms**。设置值从 `'click'` 迁移到 `'key'` 时在加载阶段自动转换，不会让老用户悄悄退回"自动结束"。

## 6. 人体测量学与几何推算

### 6.1 眼睛在哪

「笔记本平放桌面」这个场景决定了效果的可视区间，所以先把它算清楚：

| 量 | 取值 |
|---|---|
| 桌面高 | 750 mm |
| 椅面高 | 450 mm |
| 坐姿眼高（相对椅面） | 男 ~800 / 女 ~740 mm |
| ⇒ **眼睛高于桌面** | 约 440–500 mm |
| 眼睛离铰链水平距离 | 约 500–650 mm |
| 16" 16:10 屏有效高度 | 21.5 cm |

### 6.2 盖角 → 视线偏离屏幕法线

用"离铰链 60cm、高于桌面 45cm"建模：

| 盖角 | 偏离法线 | 你看到的 |
|---|---|---|
| 115° | 2° | 几乎完美正对 |
| **105°** | **12°** | 很好（= 平放桌面时的静止角） |
| 95° | 23° | 良好 |
| 90° | 26° | 良好，略偏 |
| 85° | 33° | 开始有轻微泛白 |
| 75° | 44° | 发灰，勉强读 |
| **70°** | **50°** | **开始吃力** |
| **60°** | **61°** | 基本读不了 |
| **55°** | **67°** | **实际不可用** |
| 45° | 79° | 全黑/反相 |

**结论：平放桌面的可视窗口大约是 105° → 65°。**也就是你能看见整个合盖动作的前 40° 左右。

这直接决定了三个参数：

- **`restAngle = 105`**，而不是原版的 90：屏幕正对你眼睛的角度是 105°，用 90° 会出现"合了半天效果才出来"的死区。
- **`viewingDistance = 3`**：`reach = 21.5 × vd − 2.78 = 60cm` → `vd ≈ 2.9`。原版默认 6 假设的眼睛距离比笔记本平放桌面实际情况远得多。
- **`foldAngle = 50`**：约 50° 之后面板基本看不清了，继续折只会把画面埋进黑里。

一个有意思的附带结果：**可视窗口只有约 40°，所以代理信号根本不需要覆盖 0–180°**，只需要在这 40° 窄带里单调、可重复。这个观察大幅降低了追踪器的精度门槛——实际上要求只有 ±3° 左右，而摄像头方案有 200 倍余量。

## 7. 验证方法论

这个项目里最有价值的产出可能不是效果本身，而是**这套让错误无处藏身的办法**。

### 7.1 六种手段

| 手段 | 命令 | 解决什么问题 |
|---|---|---|
| **离屏渲染成 PNG** | `npm run selftest` | 几何"错得很像对的"。红/绿条能立刻暴露翻转与转置 |
| **合成画面自检** | `npm run recon:selftest` | 把**已知位移**喂给同一套算法，不碰真实摄像头。验证的是算法本身 |
| **探针** | `__winDuoProbe(x, y)` | 把 shader 在某个屏幕点的计算结果**读回来**，而不是从照片上猜 |
| **运行轨迹落盘** | `last-run.json` / `runs.log` | 每次运行 100ms 采样（travel / peak / progress / angle / quality / strips / fps）。"画面看起来不对"这件事，只有轨迹能解释 |
| **真实屏幕截图** | `npm run shot:fold` | 数字全过但看着还是错，只有看图才知道。用合成摄像头把折角**保持住**再截 |
| **覆盖检查** | `npm run diagnose:cover` | 把覆盖层涂成纯红、逐点检查屏幕哪些区域漏。亮度检查看不见一条窄带 |

其中**探针**和**运行轨迹**是抓住 §5.2 和 §5.5 这两个最难 bug 的直接原因。

`shot:fold` 还暴露过一个测量陷阱：一开始它在扫掠过程中抓帧，而**一次截屏要花掉大半秒、会把渲染循环饿死**，抓到的帧和它声称的角度根本对不上。改成用合成摄像头把折角保持住再截才可靠。

### 7.2 测试脚本自己出的洋相

**这部分值得单独列出来，因为每一次都让人误以为功能坏了。**

1. **单实例锁让检查静默"通过"。** 用户的 Win Duo 还在后台跑（6 个 electron 进程，其中一个烧了 110 秒 CPU），于是每一次检查都在启动瞬间被单实例锁挡住、静默退出、**退出码 0、零输出**。看起来像"检查通过了"，实际上根本没运行。修法：无界面的检查模式跳过单实例锁。

2. **`app.exit()` 吞掉 stdout。** 它不等待输出排空；stdout 是管道时（也就是每一次 CI 运行、每一次 `| Select-String`），最后几次写入直接丢失。修法：加 `exitAfterFlush(code)`。

3. **硬编码的阈值压在合法运动上。** 平滑度检查用固定 25 行/采样做阈值，而合成驱动的**真实速度**就是 24–27 行（取决于当次帧率），于是随机失败。修法：阈值改成和运行自身比较——驱动是对称的，所以"展开速度不超过合上速度"就说明是平滑跟随而不是台阶。

4. **验证运行写坏了用户的设置文件。** 用合成画面跑的那次，"行程峰值"被喂进了标定逻辑并保存，用户的 `fullTravel` 从 178 变成了 167。修法：报告里带上 `synthetic` 标记，标定直接跳过。

5. **测试假设了不成立的配置。** `verify-camera` 第一段假设"盖子回位会自动释放"，而用户已经按需求把 `releaseOn` 设成了 `key`（永不自动释放）——于是它一直等到超时。修法：那一段强制用 `auto` 并把这件事打印出来；每轮的覆盖参数不写回设置。

6. **测试钩子报告成功却什么都没做。** 抓帧脚本用 `while (hook.offset < target)` 循环，而钩子**根本没暴露 `offset`**——比较对象是 `undefined`，循环跑 0 次，函数返回成功。修法：补上 getter，并改成**计数式循环**，不依赖条件判断。

7. **测试运行删掉了用户的设置。** 早期为了拿到干净默认值，几次直接删了 `settings.json`，把用户的调参结果一起删了。这是纯粹的失误，后面改成从不删除、只迁移。

**共同点**：这些坑全部属于"看起来成功了但实际没跑"或"看起来坏了但实际是测试的错"。所以每一条都补成了断言或修复。

### 7.3 CI 只做减法

GitHub Actions 上只跑 `node --check`（每个源文件解析）和 `npm install --ignore-scripts`（跳过 Electron 二进制下载）。

**深度检查故意留在本地**：它们需要真实显示器、能跑 WebGL2 的 GPU，`verify` 还需要一块屏幕可以看。这些在托管 runner 上都不存在，硬塞进 CI 只会得到一个骗人的绿勾。

## 8. 如果要复刻，注意什么

按"最容易踩"排序。

**1. 先确认传感器到底有没有。**不要只信文档。用 §2.1 那份探测清单实测一遍。而且**注意异步接口的陷阱**——`GetDefaultAsync()` 返回的对象永远不为 null，会对你误报存在。

**2. 别用眼睛判断几何对不对。**离屏渲染成 PNG，图上放带方向的标记（我们用了红/绿条）。坐标轴反了或矩阵转置了，画出来的东西依然"挺像"。

**3. 透明窗口里，"范围外"必须是不透明黑。**这是这个项目最大的一个 bug，而且看代码看不出来。

**4. 死区、阈值一律不要按"每帧"写。**帧率 20Hz 和 120Hz 之间差了六倍，同一个每帧阈值在两边行为完全不同。放在累加器上。

**5. 不要假设运动方向。**画面往哪个方向移动取决于摄像头怎么装的、用户怎么坐。从最大位移里判定，并且允许重新判定。

**6. 不要用 hold-then-release 式的棘轮。**它会"冻住 → 跳一下"。要抑制短暂反向，用**非对称跟随**（上升瞬间跟、下降按时间常数滑），它一样能抗噪，但是平滑的。

**7. 触发键只在运行期间注册。**全局快捷键会把它从所有程序手里抢走，一直挂着会让别的软件失效。

**8. 把每次运行的轨迹写进文件。**"画面看起来不对"这种反馈，没有轨迹就只能靠猜。这一条直接决定了 §5.5 能不能被找到。

**9. 找一个真实参考素材逐帧对照。**我们的折叠范围错误（§5.6）是靠抖音那段视频逐帧抽出来才发现的——视频里的人只合到 50°，而这个事实在静态截图里完全看不出来。

**10. 校准要自动且免费。**满行程取决于摄像头、房间和坐姿，写死不可能对。每次完整合盖学习一次，每轮重新归零以消除累积漂移。

**11. 想清楚"范围"这件事。**效果不需要、也不应该跟着盖子折到底：面板在约 50–65° 之后就看不清了，继续折只会把画面埋进黑里。几何角度要封顶（`foldAngle`），而不是只夹进度。

**12. 设置文件是持久化的。**改了默认值对已经跑过一次的安装**不生效**。要么提供"恢复默认"，要么在加载时做迁移（我们用这个处理了 `releaseOn` 从 `'click'` 到 `'key'`）。

**13. Windows 会把窗口裁到工作区**，任务栏那一条会漏出来。要在 `showInactive()` 之后重新 `setBounds()`。

**14. 一次截屏约 0.5 秒，且与分辨率无关。**这是采集会话的建立开销。如果可接受就接受，不要指望调小分辨率能优化它。

## 9. 仓库结构

```
src/main/         Electron 主进程
  index.js          启动、托盘、热键、IPC、触发、标定、Esc 退出键
  overlay.js        覆盖层窗口：边界、穿透点击、置顶
  capture.js        一次截屏
  defaults.js       所有可调参数
  preferences.js    设置持久化与迁移
  selftest.js       把各角度渲染成 PNG
  verify.js         证明覆盖层确实合成在桌面之上
  verify-camera.js  用合成画面跑通整条实时追踪链路
  shot-fold.js      真实屏幕在几个保持住的折角截图
  diagnose-cover.js 覆盖层覆盖网格检查
  timing.js         待命延迟测量
  check-settings.js 设置页冒烟测试
  icon.js           用代码画托盘图标（仓库里没有二进制素材）
src/renderer/     效果本体
  overlay.js        WebGL2 初始化、帧循环、待命/追踪/释放策略
  lib/lid-tracker.js  摄像头追踪器（与侦察器共用）
  lib/geometry.js   画面落在哪里
  lib/homography.js 四个角点 → 射影矩阵
  lib/shader.js     整个观感，一个 fragment shader
  lib/spring.js     临界阻尼弹簧
  lib/gradient.js   模糊与压暗曲线
src/shared/strings.js   中英界面文案
tools/lid-recon/  当初用来找到角度源的测量仪器
tools/            其他诊断工具（截屏基准、窗口边界探针、图标生成、
                  文档配图、桌面快捷方式、视频抽帧）
docs/             本文档与配图
```

规模（项目中途的一次统计）：`src` 下 22 个 `.js` 文件共 3060 行，其中效果本体 7 个文件约 1250 行。
